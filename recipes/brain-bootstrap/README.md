# Brain Bootstrap

> One command takes an empty Supabase project to a working Open Brain with the wiki and CRM stack, verifies it, and hands you a Deploy-to-Vercel link for the dashboard.

## What It Does

A fresh Open Brain install normally means an hour of copy-pasting SQL, running CLI deploys, and wiring environment variables across six READMEs. `bootstrap.mjs` collapses that into a single script: it applies the core schema plus the schemas your chosen bundle needs (in the right order), deploys the matching Edge Functions, sets the secrets, and runs the repo's smoke tests so you know the surfaces actually work before you walk away. It finishes by printing the exact environment values for the dashboard and a one-click Vercel deploy link.

It does **not** create the Supabase project for you. Creating a project consumes a paid slot on your account, so that stays a human step (two minutes, covered below). It also does not migrate any existing data or configure MCP connectors inside your AI client. See [what this does not do](#what-this-does-not-do).

## Prerequisites

- A **Supabase account** with a project already created (the [2-minute manual create](#create-a-supabase-project-2-minutes) is below). This recipe installs into an existing project.
- A **Supabase personal access token** (Management API token) exported as `SUPABASE_ACCESS_TOKEN`. Create one at [supabase.com/dashboard/account/tokens](https://supabase.com/dashboard/account/tokens). The token acts on your account, so the script uses it to apply SQL and deploy functions. Treat it like a password.
- The **Supabase CLI** on your `PATH` (only needed when functions will be deployed). Install per the [official CLI guide](https://supabase.com/docs/guides/local-development/cli/getting-started). Verify with `supabase --version`. No Docker is required — the script deploys with `--use-api`.
- **Node.js 20 or newer**. The script uses only the Node standard library, so there is nothing to `npm install`.
- Optional but recommended: an **`OPENROUTER_API_KEY`** (or `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`) in your environment. Semantic search, capture metadata extraction, and the wiki-profile worker's synthesis all need an LLM key. The script passes any it finds through to the functions as secrets.

### Create a Supabase project (2 minutes)

1. Go to [supabase.com](https://supabase.com) and sign in.
2. Click **New Project**, pick an organization, name it (`open-brain` is fine), set a database password, and choose the region closest to you.
3. Click **Create new project** and wait one to two minutes for it to provision.
4. Copy your **Project ref** — the random string in the dashboard URL `supabase.com/dashboard/project/THIS_PART`. You pass it to the script as `--project-ref`.

## The One Command

From the recipe folder in your checkout:

```bash
cd recipes/brain-bootstrap

SUPABASE_ACCESS_TOKEN=sbp_your_token \
OPENROUTER_API_KEY=sk-or-your_key \
node bootstrap.mjs --project-ref YOUR_PROJECT_REF --yes
```

That installs the default `wiki-crm` bundle: the full stack with both the wiki and CRM surfaces. Drop `--yes` to review the plan and confirm before anything is applied. Add `--dry-run` to print the plan and exit without touching the network.

### Bundles

Pick the surface you want with `--bundle`:

| Bundle | Schemas applied | Edge Functions deployed | Verified by |
|--------|-----------------|-------------------------|-------------|
| `core` | core, workflow-status, enhanced-thoughts | open-brain-rest | live-smoke |
| `wiki` | core stack + entity-extraction, typed-reasoning-edges, wiki-pages | open-brain-rest, wiki-mcp, wiki-profile | live-smoke, wiki-smoke, wiki-profile health |
| `crm` | core stack + crm-core, crm-engagement | open-brain-rest, crm-mcp | live-smoke, crm-smoke |
| `wiki-crm` (default) | all of the above | open-brain-rest, wiki-mcp, crm-mcp, wiki-profile | live-smoke, wiki-smoke, wiki-profile health, crm-smoke |

### Flags

| Flag | Effect |
|------|--------|
| `--project-ref <ref>` | Target project ref. Required for a live run. |
| `--bundle <name>` | `core`, `wiki`, `crm`, or `wiki-crm` (default). |
| `--dry-run` | Print the full plan (ordered schemas, functions, secrets, verification) and make no network calls. |
| `--skip-functions` | Apply SQL only. Skips the CLI deploy and secrets. |
| `--skip-verify` | Do not run the health check or smoke scripts. |
| `--yes` | Skip the confirmation prompt. |
| `--repo-root <path>` | Override the checkout root if you run the script from outside `recipes/brain-bootstrap/`. |

## What Gets Applied, and Why the Order

The script applies SQL through the Supabase Management API query endpoint (`POST https://api.supabase.com/v1/projects/{ref}/database/query`), authorized with your access token as a bearer token. That is the same token scope Supabase documents for automating project changes. Core setup goes first, then the bundle's schemas in an order that respects every prerequisite the schemas themselves enforce:

1. **Core setup** — the `thoughts` table, the `match_thoughts` search function, row-level security, the service-role grant, and the `content_fingerprint` column with `upsert_thought`. This is the exact SQL from [Getting Started](../../docs/01-getting-started.md) Steps 2.2–2.6, folded into one idempotent script. Everything else references `public.thoughts`.
2. **workflow-status** — adds the `status` columns. It comes before enhanced-thoughts because the enhanced `upsert_thought` writes to `status`, and `open-brain-rest` lists it in its required database shape.
3. **enhanced-thoughts** — typed columns plus the `search_thoughts_text` and `brain_stats_aggregate` RPCs the wiki-profile worker calls. Needs `content_fingerprint` and the status column above.
4. **entity-extraction** — the `entities`, `edges`, and `consolidation_log` tables. Its trigger reads `content_fingerprint`, so core must exist first.
5. **typed-reasoning-edges** — the `thought_edges` table. It hard-fails without the `edges` table from entity-extraction, so it always follows it.
6. **wiki-pages** — the persistent wiki tables and the regeneration guard. Standalone on top of core.
7. **crm-core** — editable contacts and the field-proposal truth layer.
8. **crm-engagement** — notes, tasks, and the keep-in-touch queue. Its foreign keys reference `crm_contacts`, so crm-core always precedes it.

Each schema file ships idempotent (`IF NOT EXISTS`, `CREATE OR REPLACE`), and the installer never wraps them in anything destructive. Re-running the whole command is safe: applied schemas no-op, functions redeploy, and secrets overwrite in place.

Edge Functions deploy with the Supabase CLI using `--use-api --no-verify-jwt`. Three of the four functions are self-contained; the `wiki-profile` worker imports a shared helper folder, so the script stages it into a temporary working directory with the shared folder as a sibling before deploying, then cleans the directory up. A failed function deploy is reported per-function and does not abort the rest — your SQL stays applied.

The installer always deploys whatever version of each function is in your checkout, and `open-brain-rest` is the most version-sensitive of them: the wiki milestone adds the `/wiki/*` route group (and its `wiki-smoke.mjs` harness) to the gateway alongside the existing `/crm/*` routes, and this recipe lands after that milestone, so a normal checkout deploys a gateway that serves both. The verification step detects which harnesses your checkout actually has — if `wiki-smoke.mjs` is missing (a checkout that predates the milestone), it reports an explicit SKIP for that line rather than failing. The dashboard is tolerant in the same direction: it feature-detects `/wiki` on the deployed gateway and shows a setup card instead of erroring if the gateway predates the routes.

A `--dry-run` prints the plan and exits. A live `wiki-crm` run ends like this (values abbreviated):

  applying workflow-status ... ok
  applying enhanced-thoughts ... ok
  ...
  [ok]   8 schema step(s) applied (idempotent — safe to re-run).

== 3. Deploy Edge Functions
  deploying open-brain-rest ... ok
  deploying wiki-mcp ... ok
  deploying crm-mcp ... ok
  deploying wiki-profile ... ok
  [ok]   4 function(s) deployed.

== 4. Set secrets
  [ok]   MCP_ACCESS_KEY, OPENROUTER_API_KEY set (one call, via temporary env file).

== 5. Verify
  gateway /health         PASS  200 ok
  live-smoke.mjs          PASS  open-brain-rest smoke passed (cleaned 3 rows).
  wiki-smoke.mjs          PASS  wiki smoke passed.
  wiki-profile /health    PASS  200 ok (worker live)
  crm-smoke.mjs           PASS  crm smoke passed (cleaned contact ...).

== 6. Finish — dashboard + Vercel
  Dashboard environment (open-brain-dashboard-pro):
    NEXT_PUBLIC_API_URL=https://YOUR_PROJECT_REF.supabase.co/functions/v1/open-brain-rest
    SESSION_SECRET=<generated, shown once>

  >>> SAVE THIS NOW — generated MCP access key (shown once) <<<
      MCP_ACCESS_KEY=<generated, shown once>

  Deploy the dashboard (one click):
    https://vercel.com/new/clone?repository-url=...&root-directory=dashboards/open-brain-dashboard-pro&env=...

The script exits non-zero if any surface fails, so it is safe to gate a setup script on it. The `MCP_ACCESS_KEY` and `SESSION_SECRET` are printed once — save them before you close the terminal.

> [!IMPORTANT]
> The first live run is what proves the install end to end. This recipe was authored and verified with `--dry-run` against the checked-out schemas and functions; a live Supabase project is what the smoke step exercises. If you are the first to run it live and a smoke check fails, the failing line names the surface and the [troubleshooting](#troubleshooting) table maps it to the README that owns it.

## Deploy the Dashboard to Vercel

The script prints a **Deploy to Vercel** link at the end. The Vercel deploy flow supports a monorepo subfolder, so the link sets **Root Directory** to `dashboards/open-brain-dashboard-pro` for you and pre-fills `NEXT_PUBLIC_API_URL` with your gateway URL. You paste the `SESSION_SECRET` the script generated (secrets are never embedded in a URL).

[![Deploy with Vercel](https://vercel.com/button)](https://vercel.com/new/clone?repository-url=https%3A%2F%2Fgithub.com%2Falanshurafa%2FOB1&root-directory=dashboards%2Fopen-brain-dashboard-pro&env=NEXT_PUBLIC_API_URL%2CSESSION_SECRET&envDescription=NEXT_PUBLIC_API_URL%20is%20your%20open-brain-rest%20URL%3B%20SESSION_SECRET%20is%20any%2032%2B%20char%20random%20string&envLink=https%3A%2F%2Fgithub.com%2Falanshurafa%2FOB1%2Ftree%2Fmain%2Fdashboards%2Fopen-brain-dashboard-pro%23configuration&project-name=open-brain-dashboard)

If you prefer to do it by hand: import the repo in Vercel, set **Root Directory** to `dashboards/open-brain-dashboard-pro`, then add `NEXT_PUBLIC_API_URL` (your gateway URL) and `SESSION_SECRET` (any 32+ character string) under Environment Variables. Full dashboard configuration, including the optional `WIKI_PROFILE_URL` and CRM/wiki nav toggles, is in the [dashboard README](../../dashboards/open-brain-dashboard-pro/README.md#configuration).

## Re-run Safety

Running the command again is the supported way to add a surface or recover from a partial run. Schemas are idempotent, so re-applying them changes nothing. Functions redeploy from the current checkout. Secrets are overwritten in place. If you supply `MCP_ACCESS_KEY` in the environment, the script uses yours instead of generating one, so re-runs keep the same key. The only value that changes across runs is the `SESSION_SECRET` printed at the end — that is a fresh suggestion each time, not something stored on the project, so keep the first one you saved.

## What This Does NOT Do

- **Create the Supabase project.** That costs a project slot and is a deliberate human action. Create it first (two minutes, above).
- **Migrate or import any data.** It sets up the schema and functions. To pull in real data afterward, see the import recipes under [`recipes/`](../) (Gmail, ChatGPT, Obsidian, Readwise, and more).
- **Configure MCP connectors in your AI client.** Connecting Claude Desktop, ChatGPT, Claude Code, or Cursor to your brain is covered in [Getting Started](../../docs/01-getting-started.md) Step 7. The bootstrap gives you the URL and access key those steps need.
- **Deploy the dashboard.** It hands you a one-click link and the exact env values; the click is yours.

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| `SUPABASE_ACCESS_TOKEN is required` | No access token in the environment | Create a personal access token at [account/tokens](https://supabase.com/dashboard/account/tokens) and export it. Use `--dry-run` to preview without one. |
| `Access token rejected (HTTP 401/403)` | Token invalid, revoked, or wrong scope | Regenerate the token. It must be a personal access token, not the project's anon/service key. |
| `Project '...' not found (HTTP 404)` | Wrong ref, or the token's account does not own the project | Recheck `--project-ref` against `supabase.com/dashboard/project/THIS_PART`. |
| `Supabase CLI not found on PATH` | CLI missing while functions are due to deploy | Install per the [CLI guide](https://supabase.com/docs/guides/local-development/cli/getting-started), or pass `--skip-functions` to apply SQL only. |
| A function shows `FAILED` in step 3 | Deploy error for that one function (auth, network, source) | Read the per-function message. Your SQL is already applied; re-run to retry the deploy, or deploy that function by hand from its folder under [`integrations/`](../../integrations/). |
| `gateway /health` returns FAIL | Gateway not deployed, or `MCP_ACCESS_KEY` mismatch | Confirm `open-brain-rest` deployed. If you set your own `MCP_ACCESS_KEY`, make sure it matches the one used at verify time. See [`integrations/open-brain-rest`](../../integrations/open-brain-rest/README.md). |
| `live-smoke.mjs` FAIL | Core surface issue (capture, search, browse) | Check the failing assertion in the smoke output. Semantic search and capture need `OPENROUTER_API_KEY` set on the gateway. See [`integrations/open-brain-rest`](../../integrations/open-brain-rest/README.md). |
| `crm-smoke.mjs` FAIL | CRM routes or schemas missing | Confirm the `crm` or `wiki-crm` bundle ran and `crm-mcp` deployed. See [`schemas/crm-core`](https://github.com/NateBJones-Projects/OB1/blob/main/schemas/crm-core/README.md) and [`schemas/crm-engagement`](https://github.com/NateBJones-Projects/OB1/blob/main/schemas/crm-engagement/README.md). |
| `wiki-smoke.mjs` FAIL | Wiki routes or schemas missing on the deployed gateway | Confirm `schemas/wiki-pages` applied and that the deployed `open-brain-rest` includes the `/wiki/*` route group (deploy from a checkout at or after the wiki milestone). See [`integrations/open-brain-rest`](../../integrations/open-brain-rest/README.md). |
| `wiki-smoke.mjs` SKIP | Your checkout predates the wiki milestone, so the harness file is absent | Expected on merged main. Update your checkout (pull `main`) and re-run if you want the wiki surface exercised end to end. |
| `wiki-profile /health` FAIL | Worker not deployed | Confirm the `wiki` or `wiki-crm` bundle ran. The worker needs `schemas/enhanced-thoughts` and `schemas/wiki-pages`. See [`integrations/consolidation-workers`](../../integrations/consolidation-workers/README.md). |
| Wiki-profile runs but sections are empty | No LLM key, or too few thoughts yet | Set `OPENROUTER_API_KEY` (or `OPENAI_API_KEY` / `ANTHROPIC_API_KEY`) and capture some thoughts first, then regenerate from the dashboard. |
